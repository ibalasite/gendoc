§1. Executive Summary

This document describes the engineering design of the pixel-pet-arena project, including architecture, data model, API design, and operational concerns. It covers 21 sections in total.

§2. System Architecture Overview

The system follows a Modular Monolith pattern with 6 Bounded Contexts: Identity, Pet, Arena, Leaderboard, Marketplace, and Admin. Each BC owns its own data and exposes Public APIs and Domain Events.

§2.1 Context Map

Inter-BC communication uses Domain Events for async + Public APIs for sync.

§3. Technology Stack & ADRs

Backend: Node.js 20 / Fastify 4. Database: PostgreSQL 15 (Supabase). Cache: Redis 7 (Upstash). Frontend: React 18 + Phaser.js 3.

§3.2 ADR-001: Backend stack

Chose Node.js + Fastify over Go/FastAPI for team velocity.

§4. Module / Component Design

Each BC is a separate module under apps/api/src/<bc>/ with its own routes, services, repositories.

§5. API Design

RESTful endpoints under /api/v1/* for player, /admin/api/* for admin. Auth: pet token (URL-based) for player, TOTP+session for admin.

§6. Data Model

12 PostgreSQL tables + 6 Redis key patterns. Cross-BC FKs forbidden (HC-1 hard constraint).

§7. Key Sequence Flows

Claim flow: email → OTP → token. Arena battle: matchmaking → POST /arena/battle → animation. GDPR erasure: request → 24h SLA → background job.

§8. Error Handling & Resilience

Bulkhead pattern, circuit breaker on external APIs, exponential backoff on retry.

§9. Security Design

STRIDE threat model + OWASP Top 10 coverage. RBAC for admin operations.

§10. Observability Design

SLO/SLI, structured logs, audit log retention 2 years.

§11. Performance Design

Capacity planning: 10K MAU, p95 API latency < 200ms.

§12. Testing Strategy

Unit ≥ 80% coverage, integration via Supabase local stack, E2E Playwright.

§13. Deployment & Operations

Vercel CDN + Railway containers. ArgoCD GitOps for k8s.

§14. Risk Assessment

Top risks: Phaser.js bundle size, Redis cost at scale, GDPR compliance.
